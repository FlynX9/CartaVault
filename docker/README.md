# CartaVault v1 Docker deployment

This directory contains the supported v1 deployment lifecycle. Alembic is the
single source of truth for the application schema. PostgreSQL initialization
creates only the required `postgis` and `pgcrypto` extensions.

## Image contract

Build and deploy PostgreSQL, backend/migration, and frontend images with the
same immutable version:

```powershell
.\docker\build.ps1 -Version "1.0.0"
.\docker\export-images.ps1 -Version "1.0.0" -OutputDirectory "D:\docker-exports"
```

The migration job deliberately reuses the backend image with the same tag.
There is no separate image whose code could drift from the application.

## Quick installation

Copy the template and generate all persistent secrets before starting the
stack:

```sh
cp docker/.env.example docker/.env
docker compose --env-file docker/.env -f docker/compose.setup.yml \
  run --rm setup generate-secrets
```

The command is idempotent: existing secrets are preserved. It prints the
one-time web setup token only when that token is first generated. Store that
token temporarily, then open the public CartaVault URL after the stack is
healthy. The six-step web wizard checks PostgreSQL/PostGIS, migration state,
storage, public URL, HTTPS and cookie settings before creating the first
administrator. Once an active administrator exists, every `/setup` write
endpoint is permanently locked.

Start the integrated PostgreSQL deployment:

```sh
docker compose --env-file docker/.env -f docker/compose.yml up -d
```

No manual Alembic command is part of installation or upgrade.

## Required configuration

At minimum configure:

- `CARTAVAULT_VERSION`, with an immutable value such as `1.0.0`;
- `POSTGRES_DB`, `POSTGRES_USER`, and `POSTGRES_PASSWORD`;
- `DATABASE_URL`, using the Compose host `postgres`;
- `FRONTEND_PUBLIC_URL` and `CORS_ALLOWED_ORIGINS`;
- `CARTAVAULT_SESSION_SECRET`, `CARTAVAULT_SETUP_TOKEN`, and
  `CARTAVAULT_CREDENTIALS_ENCRYPTION_KEY`, generated by the setup command;
- `EMAIL_FROM_ADDRESS`;

Copy `docker/.env.example` to `docker/.env`, replace every placeholder, and
URL-encode reserved characters in the password embedded in `DATABASE_URL`.
Never commit the resulting `.env` file.

The three `CARTAVAULT_BOOTSTRAP_ADMIN_*` variables remain optional only for
legacy unattended deployments. New installations must leave them empty and
use the one-time web wizard.

For Portainer, use `compose.portainer.yml`. `CARTAVAULT_DATA_ROOT` defaults to
`/volume2/docker/cartavault`, and can be changed to another absolute Synology
path. For a registry, set `CARTAVAULT_IMAGE_PREFIX`, for example
`ghcr.io/flynx9/cartavault`.

## External PostgreSQL/PostGIS

Use `compose.external.yml` when PostgreSQL is managed outside the stack:

```sh
docker compose --env-file docker/.env -f docker/compose.external.yml up -d
```

Set `DATABASE_URL` to the external PostgreSQL endpoint. The database user must
be able to create/alter objects in the target schema and the database must
provide PostGIS and pgcrypto. Restrict inbound PostgreSQL traffic to the
CartaVault host. The same one-shot migration job, advisory lock, setup wizard,
backup policy and application images are used.

## Clean installation

The documented deployment command is:

```sh
docker compose -f docker/compose.yml up -d
```

Compose waits for the final PostgreSQL server, runs the one-shot migration job,
starts the backend only after that job exits successfully. The first
administrator is then created by the protected web wizard. For a legacy
pre-authentication database, the job can still use the optional bootstrap
variables to assign orphaned maps before completing every Alembic head. The
job requires multiple stable SQL checks, acquires a
PostgreSQL advisory lock, and reports each phase separately.

In Portainer, deploying the stack performs the same sequence. A failed
`migrate` container intentionally leaves `backend` and `frontend` stopped.
Inspect its logs before retrying.

## Upgrade

1. Build or pull one complete image set with a new immutable version.
2. Create and verify a backup before changing the stack.
3. Change only `CARTAVAULT_VERSION`.
4. Redeploy the stack.
5. Confirm that `migrate` exited with code 0, then verify backend/frontend
   health.

Never run two hand-written Alembic commands during rollout. Concurrent stack
deployments serialize on the advisory lock.

## Backup

The complete operational runbook, including automation, integrity checks,
retention, recovery on a new host, and the encryption-key warning, is in
[`docs/backup-and-restore.md`](../docs/backup-and-restore.md).

Standard Compose:

```sh
./docker/backup.sh /srv/backups/cartavault
```

Portainer/Synology:

```sh
CARTAVAULT_COMPOSE_FILE=/path/to/compose.portainer.yml \
  CARTAVAULT_COMPOSE_PROJECT=cartavault \
  ./docker/backup.sh /volume2/backups/cartavault
```

The timestamped directory contains a custom-format PostgreSQL dump, photo and
avatar archives, checksums, and a version manifest. Set
`CARTAVAULT_BACKUP_EXPORTS=true` only when temporary exports must be kept.
Copy the encryption key and other deployment secrets separately to a protected
secret store; they are intentionally never written into the backup.

## Restore test and disaster recovery

Test restores on an isolated stack and isolated ports before every release:

```sh
CARTAVAULT_COMPOSE_PROJECT=cartavault-restore-test \
CARTAVAULT_RESTORE_CONFIRM=restore \
  ./docker/restore.sh /srv/backups/cartavault/20260729T120000Z
```

The restore script verifies checksums, stops application services, restores the
database and media, runs the version-matched migration job, then restarts the
application. Never point a restore test at the production stack.

## Rollback policy

Do not use `alembic downgrade` as an application rollback mechanism.
CartaVault migrations follow **expand / deploy / contract**:

1. **expand** adds backwards-compatible structures;
2. **deploy** moves application reads and writes to them;
3. **contract**, in a later release, removes obsolete structures.

While the deployed migrations remain compatible, roll back by restoring the
previous `CARTAVAULT_VERSION` image set. If a contract migration has run, use
the verified pre-upgrade database and media backup instead.

## Reverse proxy

Publish only the frontend HTTP port. Keep PostgreSQL and backend on the
internal Compose network. Your TLS reverse proxy must forward the public host
to `${CARTAVAULT_HTTP_PORT}` and preserve `Host`, `X-Forwarded-Proto`,
`X-Forwarded-For`, and WebSocket upgrade headers. Set:

```dotenv
FRONTEND_PUBLIC_URL=https://cartavault.example.com
CORS_ALLOWED_ORIGINS=https://cartavault.example.com
CARTAVAULT_COOKIE_SECURE=true
```

Example Nginx location:

```nginx
location / {
    proxy_pass http://127.0.0.1:8088;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
}
```

For Caddy, `reverse_proxy 127.0.0.1:8088` supplies the forwarded headers.
For Traefik, route the HTTPS service to frontend port 80. On Synology, create a
reverse-proxy rule to the NAS HTTP port configured by
`CARTAVAULT_HTTP_PORT`, enable WebSocket support and attach the certificate.

## Troubleshooting

- `migrate` must exit with code 0 before backend/frontend start. Read its logs;
  do not bypass it.
- A failed database readiness check usually means the hostname, firewall,
  password encoding, PostGIS extensions, or schema permissions are wrong.
- If the wizard reports an invalid token, regenerate only that token with
  `generate-secrets --rotate-setup-token`, update the stack environment, and
  restart backend. Rotation is useful only before the first administrator.
- If `/setup` returns 404 after an administrator exists, this is intentional.
- Back up `.env` separately. Losing the credential encryption key makes stored
  provider credentials unrecoverable.
- Uploaded photos, avatars and temporary exports use separate volumes. Never
  restore only the database when media consistency matters.

## Scope

Redis, workers, S3, automated scheduling of backups, multi-architecture builds,
and CI image publication remain outside this deployment.
